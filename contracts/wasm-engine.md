## 2. WASM export signatures

### WA-1 — stub (hello_wasm)

```rust
#[wasm_bindgen]
pub fn hello_wasm() -> String {
    "ballistics-engine ok".to_string()
}
```

Validates the full pipeline end-to-end. No physics. Must appear in the built `.wasm` and be callable from JS.

### WA-2 — trajectory computation

```rust
#[wasm_bindgen]
pub fn compute_trajectory(params_json: &str, bullet_json: &str) -> String
```

- **`params_json`**: JSON object matching `TrajectoryParams` (§3.1 below)
- **`bullet_json`**: JSON object matching `Bullet` (§3.2 below)
- **Returns**: JSON string matching `TrajectoryResult` (§3.3 below)

On parse error or any internal panic, returns a JSON error envelope:
```json
{ "error": "<message>" }
```

The caller (loader.js, §4) checks for the `error` key and throws a `BallisticsEngineError`.

## 3. JSON schema at the WASM boundary

The schemas below are **identical** to the existing `be-jsonrpc-contract.md` types.  
Field names, types, and defaults are authoritative; this contract does not redefine them — it asserts they apply equally to the WASM boundary.

### 3.1 `TrajectoryParams` (input — `params_json`)

Matches `TrajectoryParams` in `be-jsonrpc-contract.md` exactly.  
Required: `bulletId`.  
Defaults must be applied inside the Rust engine (not by the caller) to match Java engine behaviour.

| Field | JSON type | Required | Default | Constraint |
|---|---|---|---|---|
| `bulletId` | string | yes | — | — |
| `zeroRangeMeters` | number | no | 100 | >0, ≤3000 |
| `maxRangeMeters` | number | no | 1000 | >0, ≤5000 |
| `stepMeters` | number | no | 25 | >0, ≤500 |
| `windSpeedKph` | number | no | 0 | ≥0, ≤200 |
| `altitudeMeters` | number | no | 0 | ≥0, ≤10000 |
| `temperatureC` | number | no | 15 | ≥−50, ≤60 |
| `sightHeightMm` | number | no | 38.1 | ≥0, ≤150 |
| `shootingAngleDegrees` | number | no | 0 | ≥−45, ≤45 |
| `windDirectionDeg` | number | no | 90 | ≥0, ≤360 |
| `dragModel` | string | no | "G1" | "G1" or "G7" |
| `twistRateInchesPerTurn` | number | no | null (disabled) | >0, ≤100 |

> **Note:** `bulletId` is accepted but unused by the Rust engine; the bullet properties come from `bullet_json`. It is included so the same `params` object used for JSON-RPC calls can be passed to the WASM boundary without transformation.

> **Divergence note (wind / altitude upper bounds):** As of PR #59, `engine/src/types.rs::validate()` only enforces `windSpeedKph ≥ 0` and `altitudeMeters ≥ 0` — no upper bound is checked. The upper bounds `≤200` and `≤10000` are sourced from `contracts/url-state.md` (the UI-level guard). These are the authoritative contract values; a future patch to `validate()` should add the corresponding upper-bound checks to bring the Rust implementation into sync.

### 3.2 `Bullet` (input — `bullet_json`)

Matches `Bullet` in `be-jsonrpc-contract.md`.

| Field | JSON type | Required | Constraint |
|---|---|---|---|
| `id` | string | yes | — |
| `name` | string | yes | — |
| `caliber` | string | yes | — |
| `bulletWeightGrams` | number | yes | >0, finite |
| `muzzleVelocityMps` | number | yes | >0, finite |
| `ballisticCoefficient` | number | yes | >0, finite |
| `bulletDiameterMm` | number | yes | >0, finite |
| `muzzleEnergyJoules` | number | yes | — |
| `description` | string | yes | — |
| `hexColor` | string | yes | — |

> **Note:** The four physics-critical fields (`bulletWeightGrams`, `muzzleVelocityMps`, `ballisticCoefficient`, `bulletDiameterMm`) are validated by `Bullet::validate()` in `engine/src/types.rs`. `muzzleEnergyJoules` is informational (displayed in the DOPE card) and is not used in RK4 integration, so no range is enforced.

### 3.3 `TrajectoryResult` (output — return value)

Matches `TrajectoryResult` in `be-jsonrpc-contract.md`.

```json
{
  "bullet":                 { "...": "Bullet fields echoed from input" },
  "request":                { "...": "TrajectoryParams echoed from input" },
  "points":                 [ { "...": "TrajectoryPoint — see §3.4" } ],
  "maxOrdinateCm":          0.0,
  "maxOrdinateRangeMeters": 0.0,
  "supersonicLimitMeters":  0.0,
  "densityAltitudeMeters":  0.0
}
```

### 3.4 `TrajectoryPoint` (element of `points`)

Matches `TrajectoryPoint` in `be-jsonrpc-contract.md`. All fields are present on every point regardless of input parameters.

```json
{
  "rangeMeters":      0.0,
  "dropCm":           0.0,
  "velocityMps":      0.0,
  "energyJoules":     0.0,
  "windDriftCm":      0.0,
  "timeOfFlightSec":  0.0,
  "moaAdjustment":    0.0,
  "mradAdjustment":   0.0,
  "spinDriftCm":      0.0
}
```

> **WA-4 integration note:** The existing `simulateBulletJS()` does not produce `moaAdjustment`, `mradAdjustment`, or `spinDriftCm` on its point objects. After WA-4 replaces `simulateBullet()` with the WASM loader, callers receive all nine fields. Existing code that only reads the previous six fields is unaffected (extra JSON fields are ignored in JS).

## 4. Loader API (WA-3)

File: `engine/loader.js` (ESM module, shipped alongside the WASM binary at `static/wasm/`).

### Exports

```javascript
/**
 * Async-initialises the WASM module once. Subsequent calls return the same
 * resolved Promise. Must be called before computeTrajectory().
 * Throws WasmUnavailableError if WebAssembly is not defined in the runtime.
 */
export async function initEngine(): Promise<void>

/**
 * Computes a trajectory using the WASM engine.
 * initEngine() must have resolved before calling this.
 *
 * @param {object} params  TrajectoryParams object (§3.1)
 * @param {object} bullet  Bullet object (§3.2)
 * @returns {object}       TrajectoryResult (§3.3)
 * @throws {BallisticsEngineError} on engine error
 */
export function computeTrajectory(params: object, bullet: object): TrajectoryResult

/**
 * Named error thrown when WebAssembly is unavailable.
 * Callers check `instanceof WasmUnavailableError` to route to the JS fallback.
 */
export class WasmUnavailableError extends Error {
  constructor(message: string)
}

/**
 * Named error thrown when the WASM engine returns an error envelope
 * ({ "error": "..." }).
 */
export class BallisticsEngineError extends Error {
  constructor(message: string)
}
```

### Behaviour requirements

1. `initEngine()` calls `WebAssembly` synchronously on first invocation. If `typeof WebAssembly === 'undefined'`, it throws `WasmUnavailableError` immediately (no fetch attempted).
2. `initEngine()` caches its Promise. Subsequent calls return the same Promise regardless of resolution state.
3. After `initEngine()` resolves, `computeTrajectory()` is a synchronous call into WASM. It serialises `params` and `bullet` to JSON strings, calls `compute_trajectory()`, parses the returned JSON string, and checks for the `{ "error": "..." }` envelope.
4. TypeScript type declarations (`ballistics_engine.d.ts`) are generated by `wasm-bindgen`. `wasm-pack build` emits them by default; `--no-typescript` would disable them. The loader additionally ships the hand-written `engine/loader.d.ts`, specified in `wasm-integration.md` §3.2.
5. The module must work in both browser and Web Worker contexts (no `window` or `document` references).

## 5. Worker message protocol (WA-5)

> **SUPERSEDED (1.2.0):** The authoritative protocol is [`wasm-integration.md`](./wasm-integration.md) §4–§5. The changes: module worker, integer `id`, new `ready` message, `name` on `error`, `pagehide` instead of `beforeunload`, and `worker.terminate()` permitted on request timeout. The text below is kept for history only. Do not implement from it.

File: `engine.worker.js` — a standard Web Worker (not a module worker, for broadest browser support).

### Incoming messages (main thread → worker)

#### `compute` request

```json
{
  "type":   "compute",
  "id":     "<unique-string>",
  "params": { "...": "TrajectoryParams (§3.1)" },
  "bullet": { "...": "Bullet (§3.2)" }
}
```

`id` is an opaque string the caller chooses (e.g. `crypto.randomUUID()`). It is echoed in the response so the caller can match results to pending requests.

#### `terminate` request

```json
{ "type": "terminate" }
```

Sent on page `beforeunload`. Worker calls `self.close()` on receipt.

### Outgoing messages (worker → main thread)

#### `result` response

```json
{
  "type":   "result",
  "id":     "<same-id-as-request>",
  "result": { "...": "TrajectoryResult (§3.3)" }
}
```

#### `error` response

```json
{
  "type":    "error",
  "id":      "<same-id-as-request>",
  "message": "<error message string>"
}
```

### Worker lifecycle requirements

1. The worker calls `initEngine()` once during its own startup (before any `compute` messages arrive). If `initEngine()` throws `WasmUnavailableError`, the worker posts a single `{ "type": "init_error", "message": "..." }` message and closes.
2. The worker handles `compute` messages sequentially (no parallel execution inside the worker). The main thread serialises requests if needed.
3. On page `beforeunload`, the main thread posts `{ "type": "terminate" }` and the worker calls `self.close()`. The main thread does not kill the worker with `worker.terminate()` (which would abandon in-flight work without a response); it relies on the graceful `terminate` message.
4. For Jest testing, the worker is mocked with a synchronous stand-in that calls `computeTrajectory()` directly. The mock must cover both the success and `WasmUnavailableError` paths.

## 6. Parity tolerance table (WA-2)

The Rust engine is a port of `BallisticsEngine.java`. Every rendered `TrajectoryPoint` field and every top-level `TrajectoryResult` field must match the Java engine output within **ε = 0.01** (absolute difference) for all 10 catalog bullets under standard conditions (zeroRange 100 m, maxRange 1000 m, step 25 m, no wind, 0 m altitude, 15 °C, 38.1 mm sight height, 0° shooting angle, G1 drag, no twist).

| Field | Type | ε |
|---|---|---|
| `rangeMeters` | TrajectoryPoint | 0.01 |
| `dropCm` | TrajectoryPoint | 0.01 |
| `velocityMps` | TrajectoryPoint | 0.01 |
| `energyJoules` | TrajectoryPoint | 0.01 |
| `windDriftCm` | TrajectoryPoint | 0.01 |
| `timeOfFlightSec` | TrajectoryPoint | 0.01 |
| `moaAdjustment` | TrajectoryPoint | 0.01 |
| `mradAdjustment` | TrajectoryPoint | 0.01 |
| `spinDriftCm` | TrajectoryPoint | 0.01 |
| `maxOrdinateCm` | TrajectoryResult | 0.01 |
| `maxOrdinateRangeMeters` | TrajectoryResult | 0.01 |
| `supersonicLimitMeters` | TrajectoryResult | 0.01 |
| `densityAltitudeMeters` | TrajectoryResult | 0.01 |

**Rounding rule:** The Java engine applies `r1()` = `Math.round(v * 10.0) / 10.0` to every `TrajectoryPoint` field. The Rust engine must apply the same rounding to match. With ε = 0.01, any residual from floating-point rounding differences is covered by the tolerance.

**Parity test corpus:** `tests/parity_tests.rs` loads golden JSON files committed to `tests/fixtures/` (one per catalog bullet, generated by the Java engine and checked in). Each fixture contains the full `TrajectoryResult`. The parity test asserts `|rust_field − java_field| ≤ 0.01` for every field on every point.

**Additional parity conditions:** Parity tests must also cover:
- G7 drag model (all 10 catalog bullets)
- Non-zero wind (16 kph, 90°)
- Non-zero altitude (1000 m)
- Non-standard temperature (0 °C, 35 °C)
- Non-zero shooting angle (10°, −10°)
- Spin drift enabled (twistRateInchesPerTurn = 10)

**Binary size gate:** `wasm-pack build --release` output (`.wasm` after `wasm-opt`) must be ≤ 150 KB gzip. Measured in CI via `gzip -9 engine/pkg/ballistics_engine_bg.wasm | wc -c`. Failure is a blocking gate.

## 8. CI additions

A new `rust-build` job is added to `.github/workflows/ci.yml`. The existing `java-build` job gains a `needs: [rust-build]` dependency and downloads the WASM artifact before running `mvn verify`.

### New job: `rust-build`

| Property | Value |
|---|---|
| Job id | `rust-build` |
| `runs-on` | `ubuntu-latest` |
| `timeout-minutes` | `30` |
| `needs` | none |

Steps, in order:

| # | Step | Exact config |
|---|---|---|
| 1 | Checkout | `actions/checkout@v6` |
| 2 | Cache Rust toolchain | `actions/cache@v5`, `path: ~/.rustup`, `key: ${{ runner.os }}-rustup-stable` |
| 3 | Cache cargo registry | `actions/cache@v5`, `path: ~/.cargo/registry`, `key: ${{ runner.os }}-cargo-${{ hashFiles('engine/Cargo.lock') }}`, `restore-keys: ${{ runner.os }}-cargo-` |
| 4 | Cache cargo build cache | `actions/cache@v5`, `path: engine/target`, `key: ${{ runner.os }}-cargo-target-${{ hashFiles('engine/Cargo.lock', 'engine/src/**') }}`, `restore-keys: ${{ runner.os }}-cargo-target-` |
| 5 | Install Rust stable | `run: rustup update stable && rustup default stable && rustup target add wasm32-unknown-unknown` |
| 6 | Install wasm-pack | `run: curl https://rustwasm.github.io/wasm-pack/installer/init.sh -sSf | sh` (cached by step 3) |
| 7 | Install cargo-llvm-cov | `run: cargo install cargo-llvm-cov --locked` |
| 8 | Cargo test | `run: cargo test --manifest-path engine/Cargo.toml` |
| 9 | Cargo llvm-cov gate | `run: cargo llvm-cov --manifest-path engine/Cargo.toml --all-features --fail-under-lines 99` |
| 10 | wasm-pack build | `run: wasm-pack build engine/ --target web --release` |
| 11 | Binary size gate | `run: gzip -9 -k engine/pkg/ballistics_engine_bg.wasm && SIZE=$(wc -c < engine/pkg/ballistics_engine_bg.wasm.gz) && echo "WASM size: ${SIZE} bytes" && [ "${SIZE}" -le 153600 ]` (153600 = 150 × 1024) |
| 12 | Upload WASM pkg | `actions/upload-artifact@v4`, `name: wasm-pkg`, `path: engine/pkg/`, `retention-days: 1` |

### Modified `java-build` job

Add `needs: [rust-build]` and one new step immediately after checkout:

| # | Step | Exact config |
|---|---|---|
| 2a | Download WASM pkg | `actions/download-artifact@v4`, `name: wasm-pkg`, `path: engine/pkg/` |
| 2b | Copy WASM to static | `run: mkdir -p src/main/resources/static/wasm && cp -r engine/pkg/* src/main/resources/static/wasm/` |

Pass `-Dskip.wasm.pack=true` to the `mvn verify` step to prevent the exec-plugin from re-running `wasm-pack build` when the artifacts are already present (see `wasm-build-pipeline.md` §6 for the Maven property).

> **Why not add Rust to `java-build` directly?** Installing the Rust toolchain takes 2–3 minutes and would push `java-build` past its 20-minute timeout when combined with the JaCoCo full build. The separate job also gates Rust failures independently before wasting Java build time.
